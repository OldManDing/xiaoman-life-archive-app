## 三、P0（阻断级）

### P0-1 生产部署下后台接口全部打不通：前端硬编码 `/api/v1`，忽略 `VITE_API_BASE_URL`

- 前端把 baseURL 写死为同源：`apps/admin/src/shared/request.ts:647-651` `baseURL: '/api/v1'`；全仓库没有任何地方读取 `import.meta.env.VITE_API_BASE_URL`（`vite.config.ts` 也没有）。
- 但构建与部署链路是按「可配置 API 地址」设计的：
  - `apps/admin/Dockerfile:4,7` 声明并导出 `VITE_API_BASE_URL`；
  - `deploy/docker-compose.prod.yml:164` 把 `${VITE_API_BASE_URL}` 作为 build args 传入；
  - `apps/admin/.env.example:1` 明确写了 `VITE_API_BASE_URL=http://localhost:3000/api/v1`。
- 而生产反代只给 `nianlun.xmlga.top`（后台）留了 `location /` → `admin:80`（`deploy/nginx/reverse-proxy.conf:32-39`），**没有 `/api` 转发**；`deploy/nginx/spa.conf` 的 `location /` 是 `try_files $uri $uri/ /index.html`。于是 `https://nianlun.xmlga.top/api/v1/...` 会被 SPA 以 200 + `text/html` 返回，axios 拿到 HTML，`unwrap()`（`request.ts:676-681`）发现 `data.code !== 0` 后抛出「请求失败，请稍后重试」——**连管理员登录都过不去**。
- 对照：Web 端是正确实现（`apps/web/src/shared/api/http.ts:34` 读取 `VITE_API_BASE_URL`，并带原生端兜底 `https://webapi.xmlga.top/api/v1`），后台与之不一致。
- 旁证：`deploy/nginx/spa.conf` 的 CSP `connect-src 'self' https://webapi.xmlga.top` 已经为跨域 API 放行，说明「后台调 webapi 域名」本来就是预期拓扑。

**修复方向**：在 `request.ts` 里改为 `baseURL: import.meta.env.VITE_API_BASE_URL?.trim() || '/api/v1'`（与 Web 端一致），或在 `deploy/nginx/reverse-proxy.conf` 的 `nianlun.xmlga.top` server 块补 `location /api/ { proxy_pass http://api:3000; }`。两者选一即可，但必须二选一。

> 判定前提：若实际生产是「同源部署 + 反代转发 /api」，本条不成立。请以真实部署方式确认后再改。

### P0-2 手机端「邀请码」页横向溢出，主按钮被挤出屏幕

- `apps/admin/src/index.css:8250-8254`（**文件最后一条规则、不在任何媒体查询内**）：
  `.admin-invite-create-controls { grid-template-columns: minmax(220px,320px) minmax(160px,220px) auto }`。
- 移动端 override 在 `index.css:5967-5969`（`@media (max-width:760px)` → `repeat(2, minmax(0,1fr))`），同优先级但**更靠前**，被最后这条覆盖成死规则；桌面 override（`index.css:7157-7162`）同样被覆盖。
- 使用处：`apps/admin/src/pages/invites-page.tsx:150`（`className="admin-search-controls admin-invite-create-controls"`）。三列最小宽度合计 ≈ 380px + 间距 + 按钮，而 375px 手机上面板可用宽约 300px。
- 后果：邀请码页整页横向滚动，「生成邀请码」按钮跑到屏幕外。

### P0-3 弹窗高于视口时无法滚动，关闭按钮/确认按钮被裁掉且无法关闭

- `.admin-modal-overlay`（`index.css:1026-1034`，另有一条重复声明在 `1036-1040`）只有 `display:grid; place-items:center; padding:20px`，**没有 overflow**；`.admin-modal`（`index.css:1051-1061`）**没有 `max-height`/`overflow`**。
- 移动端进一步变成 `place-items: end stretch`（`index.css:4379-4382`），即贴底对齐 → 弹窗顶部（含关闭按钮）被裁。
- 同时 `useDialogA11y` 会锁 `document.body.style.overflow = 'hidden'`（`apps/admin/src/shared/useDialogA11y.ts:13-14`），页面本身也滚不动。
- 受影响弹窗：操作原因确认（`shared/useOperationReasonDialog.tsx:24-53`）、完成档案交付（`pages/list-pages.tsx:410-480`）、重置密码（`:518-585`）、调整权益（`:631-707`）、修改 AI 设置（`pages/ai-settings-page.tsx:433`）。
- 项目里其实已有正确写法可抄：`.admin-ai-settings-modal`（`index.css:3803-3807`）用了 `max-height: min(860px, calc(100dvh - 40px)); overflow:auto`，但只给了一个弹窗。

### P0-4 手机端 `.admin-main` 仍是 `100dvh` 内部滚动容器 → 双重滚动条 + 底部内容被裁

- 移动端本意：`index.css:3889-3894`（`@media (max-width:760px)` 块内）`.admin-main { height:auto; max-height:none; overflow:visible }`，且 `.admin-layout` 在同一媒体块里已放开高度。
- 但文件更靠后的全局规则 `index.css:4902-4911`（顶层，同优先级、更晚）又写回 `height:100dvh; max-height:100dvh; overflow-y:auto; overscroll-behavior:contain`，把移动端设定全部覆盖（只有 padding 靠 `!important` 在 `index.css:5954-5956` 兜住）。
- 后果：文档高度 = 侧栏高度 + 100dvh，而主区域是独立滚动容器且 `overscroll-behavior:contain` 阻止滚动链，长列表页底部（通常是分页栏）够不到，顶部导航也会被滚出视野。

## 四、P1（功能/体验缺陷）

### P1-1 `viewer`（只读账号）仍显示并可点击写操作按钮，点完必然 403

后端只有 `super_admin / operator / viewer` 三种角色（`apps/api/prisma/schema.prisma:96-100`），写接口一律限制 `super_admin/operator`。前端只在部分页面做了收敛（`ai-settings-page.tsx:107`、`system-config-page.tsx:70`、`list-pages.tsx:2244,2428` 客服/档案、`:1393-1394` 重置密码与权益），**以下写操作完全没有按角色隐藏或禁用**：

| 位置 | 按钮 | 后端要求 |
|---|---|---|
| `pages/list-pages.tsx:1481` | 用户「冻结 / 解冻」 | `super_admin, operator` |
| `pages/list-pages.tsx:1664` | 记录「下架 / 恢复」 | `super_admin, operator` |
| `pages/list-pages.tsx:1834-1836` | 媒体「通过 / 标记异常 / 下架」 | `super_admin, operator` |
| `pages/list-pages.tsx:1973-1974` | AI「重试 / 取消」 | `super_admin, operator` |
| `pages/invites-page.tsx:159,123-129` | 「生成邀请码 / 撤销」 | `super_admin, operator` |

后果：只读账号点下去、填完原因，只换来一句「没有权限执行该操作，请联系超级管理员」。现有 27 个单测只覆盖 `operator`（`app/App.test.tsx:1214,1357`），没有任何 `viewer` 用例，所以这条没人守。

### P1-2 400 校验错误只显示「参数校验失败」，且操作原因长度前后端不一致

- 后端校验失败返回 `{code:1001, message:'参数校验失败', data:{fields:[{field,reason}]}}`（`apps/api/src/shared/api-exception.filter.ts:50-54`）。
- 前端只取顶层 `message`（`apps/admin/src/shared/request.ts:29-34`），**`data.fields` 被整段丢弃**；Web 端则专门解析并本地化了 `fields[].reason`（`apps/web/src/shared/api/http.ts:83-88`）——后台缺这一层。
- 叠加：原因输入框只校验「非空」（`shared/useOperationReasonDialog.tsx:42-47`；`list-pages.tsx:575-578,691-694`），而后端 DTO 一律 `@MinLength(2)`（如 `admin-update-user-status.dto.ts:10-11`、`admin-ai-job-action.dto.ts:6-8`、`admin-update-archive-export-request-status.dto.ts:8-11`）。
- 后果：只填一个字（如「急」）→ 请求 400、操作未生效、提示只有「参数校验失败」，管理员不知道哪里错了。`@MaxLength(200/500)` 前端同样没有 `maxLength` 约束。

### P1-3 抽屉里的弹窗按 Esc 会连抽屉一起关掉

`useDialogA11y` 对每个弹窗/抽屉都在 `document` 上注册捕获阶段 `keydown`（`shared/useDialogA11y.ts:22-50`），Escape 分支只调了 `event.stopPropagation()`——它**无法阻止同一节点上其它监听器**（那只对冒泡路径有效，需要 `stopImmediatePropagation`）。抽屉先打开、弹窗后打开，于是按一次 Esc：抽屉监听器先跑（关闭抽屉），弹窗监听器再跑（关闭弹窗）。

复现：用户列表 → 详情抽屉 → 「重置密码」→ 按 Esc → 弹窗和抽屉一起消失。同类现象还有：`AdminSelect` 下拉里按 Esc 想收下拉，结果把整个弹窗关掉（下拉自身的 Esc 处理在 React 根节点上，晚于 document 捕获）。

### P1-4「系统运维」页加载失败后没有任何重试入口

`pages/ops-readiness-page.tsx:236-255` 的「重新读取」按钮只在 `!loading && !readiness && !error` 时渲染——即「没有数据且没有错误」这一自相矛盾的条件。真正加载失败（`error` 有值）时页面只剩一条错误文案，什么也点不了。而总览页恰恰提示用户「请进入系统运维页重试」（`pages/dashboard-page.tsx:242`）。

### P1-5 从列表打开「调整权益」，到期日期是空的 → 有覆盖真实到期时间的风险

`listUsers` 返回的字段里没有 `membership_expire_at`（`apps/api/src/modules/admin/admin.service.ts:920-930`，前端类型 `request.ts:55-64` 也没有），但列表行的按钮把这条记录直接传进弹窗（`pages/list-pages.tsx:1490` → 类型见 `:1440`，读取见 `:616`）。结果：付费用户（家庭会员 / 增强整理会员）打开弹窗时到期日为空且被标记「必填」，管理员必须重新选一个日期，随手选错就把真实到期时间改掉了。详情抽屉路径（走 `getUserDetail`）才有该字段。

### P1-6 全局焦点圈对比度约 1.4:1，键盘用户看不到焦点

`index.css:100-107`：`outline: 3px solid rgba(150,111,45,0.28)`（第 105 行），在白底上合成为 `#e2d7c4`（≈1.42:1），在深色侧栏 `#2b2419` 上约 1.38:1，远低于 WCAG 2.4.11/1.4.11 要求的 3:1。它是除两处特例外**唯一**的焦点样式。另外 `CompactText` 的 `<span role="button" tabIndex={0}>`（`pages/list-pages.tsx:90-94`）不带 class，不在该选择器覆盖范围内，走浏览器默认样式——项目里同时存在两套焦点语言。

### P1-7 `AdminSelect` 的可见控件普遍没有可访问名称

`shared/ui.tsx:130-171`：真正的 `<select>` 被 `aria-hidden="true"` + `tabIndex={-1}` 隐藏，对外暴露的是自绘 `role="combobox"` 按钮。但该按钮没有 `aria-label`，外层 `<label>` 的隐式关联只会落到被隐藏的原生 `<select>` 上。于是媒体库、通知、审计、内容风险、系统配置等筛选器的组合框在读屏里是「组合框，空白」。只有 AI 设置页显式传了 `aria-label`（`pages/ai-settings-page.tsx:444`）。

### P1-8 手机端邀请码表格把邀请码省略号截断

`index.css:7642-7646`（`.admin-invites-table td:first-child { white-space:nowrap; overflow:hidden; text-overflow:ellipsis }`）与卡片模式规则 `.admin-responsive-table td:first-child`（`index.css:4305-4312`）同优先级且在更后，卡片模式下首列被省略号截断。邀请码正是管理员要复制粘贴的内容，手机上却看不全。

### P1-9 表格操作列宽度有三份互相冲突的定义

`.admin-table-panel .admin-responsive-table th/td:last-child` 依次被写成 `168px`（`index.css:525-528`）、`206px`（`4476-4479`）、`144px; max-width:144px`（`5146-5150`），≤760 再变 `auto`（`5595-5599`）。桌面最终 144px，减 padding 后内容盒 120px，而 `86px 按钮 + 40px 更多按钮 = 132px`（`index.css` 中 `.admin-action-group-compact` 段），8 列宽表（成长记录、邀请码）会挤/溢出。

## 五、P2（细节、一致性、可维护性）

**功能/契约类**

1. 客服反馈筛选只给了「数据异常 / 使用问题」（`pages/list-pages.tsx:2283-2286`），而用户端实际有 4 类：使用问题 / 页面显示 / 数据异常 / 功能建议（`apps/web/src/pages/profile-pages.tsx:2290-2295`）。分类是自由字符串落库（`prisma/schema.prisma:668`），另外两类无法筛选。
2. 通知投递状态筛选缺 `processing`（`pages/list-pages.tsx:2106-2112`、DTO `admin-notification-list.dto.ts:4`），但 push worker 会写这个状态（`huawei-push-delivery.service.ts`）；「版本更新」通知类型（`labels.ts:140`）后端从不产生，选了必然空列表。
3. 审计「动作」下拉漏了后端真实存在的动作：`admin_logout`、`admin_change_password`、`admin_update_ai_settings`、`admin_test_ai_settings`、`user.password_changed`、`user.archive_summary_downloaded`、`user.account_deleted`（对照 `labels.ts:205-255` 与 `admin.service.ts`）；这些动作会以原始英文串显示，且只能靠关键字搜。
4. 审计「关键字」输入框的提示是通用文案，但后端只匹配 `action` / `target_type`（`admin.service.ts:2025-2032`）——搜 IP、目标编号、UA 会静默返回 0 条。
5. 审计 `actor_id` 是自由文本（`pages/list-pages.tsx:2618`），后端要求正整数（`admin.service.ts:2035-2043`），前端无校验且错误提示仍是通用的「参数校验失败」。
6. 记录页从 URL 读取 `record_filter` 只在挂载时执行一次（`pages/list-pages.tsx:1604`），浏览器前进/后退或同路由 query 变化时，筛选标签与实际结果会不同步。
7. 总览「内容风险」卡片显示的是 `content_risks` 总数，却跳到 `/records?record_filter=risk`（记录风险标记），两个口径不同，数字常对不上；真正的风险队列 `/content-risks` 只挂在系统运维页的「风险队列」链接里（`ops-readiness-page.tsx:210`）。

**交互/可访问性类**

8. `ActionMenu` 不响应点击外部关闭（对比 `AdminSelect` 有做 `mousedown` 外部关闭），点开一行「更多操作」后再点别处不关，可同时开多个；弹层也没有 `role="menuitem"`、没有 `max-height`（`index.css:917-930`），动作多时会顶出视口。见 `pages/list-pages.tsx:312-343`。
9. 成长记录筛选容器写了 `role="tablist"`，子元素却是普通 `<button>`，没有 `role="tab"`/`aria-selected`（`pages/list-pages.tsx:1675-1690`）。
10. 列表页首帧 `loading` 初始为 `false`（`pages/list-page-state.ts:11`）且请求在 `setTimeout(0)` 里发起，会先闪一帧「暂无可处理数据」空态再进入加载态（`pages/shared.tsx:57-60`）。
11. 通知页加载失败时丢弃真实错误文案，固定显示「通知数据暂时不可用…」（`pages/list-pages.tsx:2136`），与其它页「加载失败：{原因}」不一致。
12. 灯箱缺少可见的关闭入口：媒体列表与详情抽屉的灯箱都只提供「点空白处」或 Esc（`pages/list-pages.tsx` 的 `MediaThumb` 与 `detail-drawer.tsx` 的 `MediaPreview` 各自注册了 Esc），鼠标用户不容易发现怎么退出。已在 9 月 20 日的修复中补上显式关闭按钮。
13. 图表数据点的 `:focus-visible` 规则不可达——`pages/dashboard-page.tsx:104` 的 `<circle>` 没有 `tabIndex`，`index.css:6941` 永远不触发；`AdminDateInput` 的日期占位文案对比度不足（`index.css:7578-7580`，白底约 3.44:1）；分页「跳至」输入框 placeholder 被更晚的规则改回 `#a29686`（`index.css:7609-7613`，约 2.9:1）。

**类型/健壮性类**

14. `changePassword` / `logout` 的响应类型与实际不符（`request.ts:689-697` 声明 `{changed:boolean}`，后端返回 `{success, revoked_sessions, changed_at}` / `{success}`）；目前 UI 不读，属类型谎言。
15. `AdminSelect` 用伪造事件对象回调 `onChange`（只带 `target.value`/`currentTarget.value`，`shared/ui.tsx:115-123`），且以 `option.value` 作 React key、不支持 `optgroup`；`AdminDateInput` 的日期覆盖层与原生输入并存，异常值会显示 "Invalid Date"（`shared/format.ts:3`），`toIsoDateTime` 对非法输入会抛 `RangeError`。

#### E2E 暴露的真实产品缺陷（已修）

**登出请求丢失 Authorization 头**：`auth.tsx` 在执行 `adminApi.logout()` 后**同步**清空内存 token，而 axios 的请求拦截器要等到微任务才读取 token，导致 `/admin/auth/logout` 收到 401——表现在界面上是「已退出」，但**服务端会话并没有被撤销**。修法：先把当前 token 取出来显式传给登出接口，再清本地会话。巡检里异常的控制台 401 随之消失。

## 九、当前 UI 与功能设计是否合理

总体判断：**列表页骨架是这套后台最扎实的资产，问题出在信息架构与「把运维视角当产品视角」**。分四个层面说。

### 9.1 站得住的判断

1. **列表页模式统一且完整**：查询面板 → 概览 → 表格 → 分页 → 详情抽屉，17 个页面几乎同构；加载/空/错误/成功四态都有落点，抽屉内操作也会回到全局反馈条。这在自研后台里属于少见的整齐。
2. **敏感操作「原因必填 + 写审计」的口径统一**：冻结、下架、审核、重试、交付、配置调整全部留痕，并有专门的审计页与审计动作字典，符合未成年人数据场景的合规直觉。
3. **风险归集页只做跳转、不重复处置**：内容风险页把记录、媒体、工单、AI 四类风险归一，再跳到各自队列处理，避免了「一个风险两处处置」的经典陷阱。
4. **删除类操作都给了业务后果文案**（如「基础会员无需设置到期日期」「不绑定时任何新用户都能注册」），比单纯弹确认框更有效。
5. **列表刷新采用局部状态更新**而不是整页重载，分页/筛选条件不丢，符合运营连续作业的节奏。

### 9.2 不合理或值得重做的设计

1. **导航权重与使用频率倒挂（最该改的一条）**
   侧栏把「系统运维 / 系统配置」这类低频页放在一级，而**每天要用的媒体库、内容风险完全不在导航里**，只能先点「系统运维」再点「技术媒体库 / 风险队列」进去。E2E 还固化了「侧栏不得出现 `/media`、`/content-risks`」这条断言，说明这是刻意的信息架构决策——但它服务的是「后台要显得精简」，不是「运营要少点两次」。
   建议：导航按角色给两套视图（运营视图直接暴露媒体审核、内容风险、客服反馈、档案交付；超管视图再加系统配置、运维、审计），而不是用「更多管理」弹出面板兜住 12 个二级页面。
2. **「当前页统计」会误导**
   「当前页正常 12 / 当前页已冻结 1」这类胶囊是**分页数据的统计**，在 20 条/页的列表里和总量差距可能上百倍。运营很容易把它读成总体健康度。建议要么改成后端全局统计（dashboard/ops 已有现成数字），要么明确标注「仅当前页」并弱化视觉权重。
3. **筛选状态与 URL 的关系没有统一约定**
   此前只有成长记录页尝试把筛选写进 URL（而且只在挂载时读一次）。现在这条改成了路由驱动，但其余 10 个列表页的筛选、分页、关键字仍然完全不进 URL——刷新即丢、无法分享、无法把「待处理的儿童安全工单」直接发给同事。建议统一：筛选 + 页码进 query，搜索关键字不进（避免污染历史）。
4. **「操作原因」是唯一拦截手段，缺少危险动作的差异化**
   当前所有写操作都是同一个「填原因 → 确认执行」弹窗，包括「永久下架媒体」「完成档案交付」这类不可逆动作。原因必填是对的，但对高破坏性动作还缺：受影响对象摘要（会下架几条记录 / 影响哪个家庭）、二次输入确认（如输入媒体编号后四位）、以及操作后的即时撤销入口。
5. **表单缺少结构化输入，全部退化成自由文本**
   档案交付要求填「下载地址 + SHA256 + 交付证据」，全是手填；媒体/记录也没有批量操作。这类流程本该由系统生成（后端出打包任务 → 生成带签名的下载链接与校验值 → 管理员只确认），让人手抄 SHA256 既不安全也容易出错。
6. **两步式配置容易漏步**
   AI 设置是「弹窗保存 → 再点测试连接」，且测试要求「无未保存修改」；真实使用中很容易出现「改了模型、界面显示已保存、但从未验证可用」。建议保存成功后自动跑一次连接测试并把结果内联在弹窗里。
7. **状态机没有约束可选动作**
   媒体「通过/标记异常/下架」对 `removed`、`ready`、`failed` 三种状态一视同仁；已下架的媒体还能再点「通过」，已经「已解决」的工单仍可点「关闭」。列表按钮应该由状态推导（`ready` 只给「下架」、`removed` 只给「恢复」），避免无意义的状态回环写进审计。
8. **四个页面重复实现同一套列表逻辑**
   媒体、通知、客服反馈、档案交付各自复制了「筛选状态 + 请求版本号 + 自动加载 + 分页回调」（约 100 行 × 4），与 `useAdminListPage` 并存。这类复制是后续改一处漏三处的根源，建议统一收敛到一个「带筛选的列表 hook」，各页只声明过滤字段。
9. **可访问性此前基本没有兜住**
   焦点不可见、组合框无名称、`role="tablist"` 误用、Esc 连锁关闭——这些不是样式细节，而是决定了键盘/读屏用户能否用这套后台。本次修了关键项，但还缺一次系统性的键盘走查（尤其是表格内的自绘控件与灯箱）。

### 9.3 更大的一个结构性问题：后台承担了太多「客服工单系统」的职责

档案交付、客服反馈、内容风险、儿童安全工单这四块，本质是**有 SLA、有归属人、有流转记录**的工单体系，现在被实现成四个独立列表 + 手工改状态。它们的共同缺口是：

- 没有「分配给我 / 我负责的」视图，`assigned_admin_name` 只出现在详情里；
- 没有超时提醒（提交超过 24h 未受理的儿童安全工单不会浮出来）；
- 没有跨页面的统一待办，运营只能靠总览那 4 个数字自己判断优先级。

如果这份后台还要长期演进，我建议下一步不是继续加页面，而是**加一层「待办/工单中心」**：把风险、工单、交付、媒体异常收敛成同一种「待处理事项」模型（对象、优先级、SLA、负责人、处理动作），现有四个页面退化成该模型的不同筛选视图。这与当前后端「风险按需聚合、不新增同步表」的思路并不冲突，可以先从只读聚合视图做起。

### 9.4 结论

- 作为**内部运营工具**，它已经过了「能用」这条线：结构一致、状态齐全、留痕完整。
- 作为**面向 3 个角色、每天高频使用**的系统，最该补的三件事依次是：**按角色的导航与信息架构**、**统一的筛选/深链约定**、**危险动作的差异化确认**。
- 代码层面最该做的一次性投入是**列表逻辑收敛与样式收敛**（本次未做的死 CSS/重复块也归入这一步），否则后续每加一个页面都会同时加一份重复逻辑和一层新的样式覆盖。
